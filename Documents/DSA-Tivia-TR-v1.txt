                          1. INTRODUCTION

1.1 Background
--------------
Data Structures and Algorithms (DSA) form the foundation of efficient software
engineering. While theoretical understanding of time and space complexity is
essential, the ability to select and implement appropriate data structures for
real-world problems separates competent programmers from exceptional ones. This
project applies multiple DSA concepts in an integrated system: a multiplayer
quiz game where every architectural decision is driven by algorithmic
considerations.

The quiz domain was chosen because it naturally requires:
  • Dynamic data storage (questions may be added/removed)
  • Fast lookup (player authentication)
  • Ordered storage (sorted player records)
  • Efficient sorting (leaderboard generation)
  • Persistent storage (data survival across sessions)

1.2 Problem Statement
---------------------
Conventional quiz implementations in academic settings typically use:
  • Fixed-size arrays for all data storage
  • Linear search (O(n)) for every lookup operation
  • Library sort functions (qsort()) without understanding underlying mechanics
  • No persistence — data vanishes when the program exits
  • Unfair ranking systems that don't handle ties properly

These limitations result in systems that are inefficient, inflexible, and
academically unimpressive. This project addresses each limitation through
intentional data structure and algorithm selection.

1.3 Project Objectives
------------------------
Primary Objectives:
  1. Implement a dynamic question bank using Singly Linked Lists
  2. Achieve O(1) average-case player authentication using Hash Tables with
     separate chaining
  3. Maintain lexicographically ordered player records using Binary Search Trees
  4. Implement Merge Sort from scratch for leaderboard generation
  5. Ensure fair competition through fixed question counts and competition
     ranking (1,2,2,4... style)
  6. Provide persistent data storage using text file I/O

Secondary Objectives:
  7. Compare empirical performance of Bubble Sort, Quick Sort, and Merge Sort
  8. Demonstrate proper dynamic memory management (malloc/free, valgrind-clean)
  9. Implement comprehensive input validation and error handling
  10. Generate detailed per-player result reports

1.4 Scope and Limitations
---------------------------
In Scope:
  • Console-based user interface
  • Single-machine execution
  • 20 hardcoded DSA questions (extensible design)
  • Fixed 10-question sessions for all players
  • One attempt per student ID
  • Three sorting algorithms with timing comparison

Out of Scope (Future Work):
  • Network multiplayer functionality
  • Graphical user interface
  • External database integration
  • Question difficulty classification
  • Real-time leaderboards

              2. LITERATURE REVIEW / THEORETICAL FOUNDATION

2.1 Linked Lists
----------------
A linked list is a linear data structure where elements (nodes) are stored in
non-contiguous memory locations, connected via pointers. Unlike arrays, linked
lists offer:
  • Dynamic size — grows and shrinks at runtime
  • Efficient insertion/deletion — O(1) at known position
  • No memory pre-allocation — allocates exactly what's needed

Trade-off: No random access — traversal is O(n).

Application in this project: The question bank uses a singly linked list because
questions are accessed sequentially during a quiz session. Random access is
never needed, and the list can grow without reallocation if questions are added.

2.2 Hash Tables
---------------
A hash table implements an associative array, mapping keys to values using a
hash function. Key characteristics:
  • Average-case O(1) for insertion, deletion, and lookup
  • Hash function distributes keys across buckets
  • Collisions resolved via chaining or open addressing

Hash Function Used: djb2 (Daniel J. Bernstein)
  hash = 5381
  for each character c in key:
      hash = ((hash << 5) + hash) + c   // equivalent to hash * 33 + c

This function provides good distribution for string keys with minimal
computation. Separate chaining (linked lists at each bucket) handles collisions.

Application in this project: Player authentication by Student ID. When a user
enters their ID, the system must instantly determine if they've already played.
O(1) average lookup makes this feasible even with hundreds of players.

2.3 Binary Search Trees
-----------------------
A BST is a node-based binary tree with the ordering property:
  left_subtree.keys < node.key < right_subtree.keys

Operations:
  • Search: O(h) where h = tree height
  • Insertion: O(h)
  • Inorder traversal: yields sorted sequence

For a balanced tree: h = O(log n)
For a skewed tree: h = O(n) worst case

Application in this project: The BST stores all players ordered by Student ID.
This serves two purposes:
  1. Inorder traversal produces sorted output for file saving
  2. Ordered storage enables efficient range queries if needed later

2.4 Sorting Algorithms
------------------------
Three algorithms were implemented and compared:

Bubble Sort:
  • Compare adjacent elements, swap if out of order
  • Best: O(n) — when already sorted (with optimization flag)
  • Average/Worst: O(n²)
  • Space: O(1) — in-place
  • Stable: Yes

Quick Sort:
  • Divide: pick pivot, partition array
  • Conquer: recursively sort subarrays
  • Best/Average: O(n log n)
  • Worst: O(n²) — when already sorted and poor pivot choice
  • Space: O(log n) — recursion stack
  • Stable: No

Merge Sort:
  • Divide: split array in half recursively
  • Conquer: merge sorted halves
  • All cases: O(n log n) — guaranteed
  • Space: O(n) — auxiliary arrays
  • Stable: Yes

Why implement all three? To provide empirical evidence of theoretical
complexity differences and to demonstrate mastery of each algorithm's mechanics.

2.5 Competition Ranking
-----------------------
Standard sequential ranking (1,2,3,4...) penalizes players who tie with others.
Competition ranking ("1224" style) assigns the same rank to tied scores and
skips ranks for subsequent players:

  Scores:  10, 10, 8, 8, 5
  Ranks:    1,  1, 3, 3, 5

This is the standard used in sports (Olympics), academics (percentile
ranking), and competitive programming leaderboards. It fairly represents that
tied players performed equally well.

3.3 Data Structure Selection Justification
--------------------------------------------

Requirement: Store 20 questions, possibly more in future
Options: Fixed array, Dynamic array, Linked List
Selected: Linked List
Reason: Dynamic growth without reallocation; sequential access matches quiz
        flow; demonstrates pointer manipulation
Trade-off: O(n) access time — acceptable since questions are asked sequentially

Requirement: Authenticate player by Student ID
Options: Linear search on array, Binary search on sorted array, Hash Table
Selected: Hash Table with separate chaining
Reason: O(1) average lookup; handles dynamic insertions; no sorting required
Trade-off: O(n) worst case if all keys collide — mitigated by good hash function

Requirement: Store all players in sorted order for file output
Options: Sorted array (insertion sort on insert), BST, Balanced BST (AVL)
Selected: BST
Reason: O(log n) insertion/search average; inorder gives sorted output; simpler
        than AVL for this scope
Trade-off: Can degrade to O(n) if inputs are sorted — acceptable for academic
            project with random student IDs

Requirement: Sort leaderboard by score descending
Options: Bubble Sort, Quick Sort, Merge Sort (all implemented)
Primary: Merge Sort
Reason: Guaranteed O(n log n); stable; excellent for demonstrating
        divide-and-conquer
Comparison: All three available for empirical timing comparison

4.2 Core Data Structures (Code + Explanation)

4.2.1 Question Node (Linked List)
---------------------------------
    typedef struct QNode {
        int  qno;                          // Question number (1-based)
        char question[MAX_Q_TEXT];           // Question text
        char options[4][MAX_OPT_LEN];      // Four options
        int  correctOption;                // Index 0-3 of correct answer
        struct QNode *next;                // Pointer to next node
    } QNode;

Memory Layout:
    [QNode 1] → [QNode 2] → [QNode 3] → ... → [QNode 20] → NULL

Key Operation — Traversal by Index:
    QNode* getQuestionByIndex(int idx) {
        QNode *t = g_question_head;
        for (int i = 1; i < idx && t != NULL; i++)
            t = t->next;
        return t;
    }

Time Complexity: O(n) where n = index
Space Complexity: O(1) auxiliary

4.2.2 Player Node (BST + Hash Table)
------------------------------------
    typedef struct Player {
        char  name[MAX_NAME_LEN];          // Player name
        char  studentID[MAX_ID_LEN];       // Unique identifier
        int   batch;                       // Batch number
        char  deptCode[MAX_DEPT_LEN];      // Department code
        float score;                       // Final score
        int   correct, wrong, skipped;     // Answer statistics
        int   totalQuestions;              // Questions attempted
        int   rank;                        // Competition rank

        struct Player *left;               // BST left child
        struct Player *right;              // BST right child
        struct Player *hash_next;          // Hash table chain link
    } Player;

Critical Design Decision: SINGLE NODE, MULTIPLE STRUCTURES

The same malloc'd Player node exists in BOTH the BST and Hash Table:

    malloc(Player) ──→ insertBST(root, p) ──→ BST links (left, right)
              │
              └──→ insertHash(ht, p) ──→ Hash chain link (hash_next)

This design:
  • Saves memory (no duplication)
  • Ensures consistency (update score in one place, both structures see it)
  • Demonstrates advanced pointer usage

4.2.3 Hash Table
----------------
    #define HASH_SIZE 101

    typedef struct {
        Player *buckets[HASH_SIZE];        // Array of chain heads
    } HashTable;

Hash Function (djb2):
    int hashFunc(const char *studentID) {
        unsigned long hash = 5381;
        int c;
        while ((c = *studentID++))
            hash = ((hash << 5) + hash) + c;
        return (int)(hash % HASH_SIZE);
    }

Why 101? Prime number reduces clustering and distributes keys more uniformly.

Collision Resolution — Separate Chaining:
    Bucket[i] → [Player A] → [Player B] → NULL
    (All players whose hash maps to index i)

4.3 Algorithm Implementations
-----------------------------

4.3.1 Fisher-Yates Shuffle
--------------------------
Purpose: Randomize question order without bias

    void shuffleIndices(int arr[], int n) {
        for (int i = n - 1; i > 0; i--) {
            int j = rand() % (i + 1);
            int temp = arr[i];
            arr[i] = arr[j];
            arr[j] = temp;
        }
    }

Correctness Proof:
  • Each element has equal probability of appearing in any position
  • No element is favored or disadvantaged
  • Time: O(n), Space: O(1)

4.3.2 Merge Sort (Primary Leaderboard Sort)
-------------------------------------------
    void mergeSortByScore(Player *arr[], int left, int right) {
        if (left < right) {
            int mid = left + (right - left) / 2;
            mergeSortByScore(arr, left, mid);      // Sort left half
            mergeSortByScore(arr, mid + 1, right); // Sort right half
            merge(arr, left, mid, right);           // Merge sorted halves
        }
    }

Merge Function:
    void merge(Player *arr[], int left, int mid, int right) {
        int n1 = mid - left + 1;
        int n2 = right - mid;
        Player **L = malloc(n1 * sizeof(Player *));
        Player **R = malloc(n2 * sizeof(Player *));

        // Copy data to temporary arrays
        for (int i = 0; i < n1; i++) L[i] = arr[left + i];
        for (int j = 0; j < n2; j++) R[j] = arr[mid + 1 + j];

        // Merge back in descending score order
        int i = 0, j = 0, k = left;
        while (i < n1 && j < n2) {
            if (L[i]->score > R[j]->score)
                arr[k++] = L[i++];
            else if (L[i]->score < R[j]->score)
                arr[k++] = R[j++];
            else { // Tie-breaker: studentID ascending
                if (strcmp(L[i]->studentID, R[j]->studentID) < 0)
                    arr[k++] = L[i++];
                else
                    arr[k++] = R[j++];
            }
        }
        // Copy remaining elements
        while (i < n1) arr[k++] = L[i++];
        while (j < n2) arr[k++] = R[j++];

        free(L); free(R);
    }

Complexity Analysis:
  • Time: O(n log n) — recurrence T(n) = 2T(n/2) + O(n)
  • Space: O(n) — auxiliary arrays L and R
  • Stable: Yes — equal elements maintain relative order

4.3.3 Competition Ranking Algorithm
-----------------------------------
    void assignCompetitionRanks(Player *arr[], int n) {
        if (n == 0) return;

        int currentRank = 1;
        arr[0]->rank = currentRank;  // Highest score gets rank 1

        for (int i = 1; i < n; i++) {
            if (arr[i]->score == arr[i - 1]->score) {
                // Same score → same rank
                arr[i]->rank = arr[i - 1]->rank;
            } else {
                // Different score → next available rank
                currentRank = i + 1;
                arr[i]->rank = currentRank;
            }
        }
    }

Example Trace:
  Input scores (sorted desc): [8.50, 8.50, 7.00, 7.00, 5.00]
  i=0: rank = 1
  i=1: 8.50 == 8.50 → rank = 1 (same)
  i=2: 7.00 != 8.50 → rank = 3 (skips 2)
  i=3: 7.00 == 7.00 → rank = 3 (same)
  i=4: 5.00 != 7.00 → rank = 5 (skips 4)

  Output ranks: [1, 1, 3, 3, 5]

  • Inorder BST save — produces sorted-by-ID output naturally

6.2 Algorithm Comparison
------------------------
The empirical results validate theoretical complexity:

Bubble Sort:
  • Simple to implement but impractical for n > 100
  • Best case O(n) with optimization flag rarely occurs in practice
  • Educational value: demonstrates why O(n²) is unacceptable

Quick Sort:
  • Fastest in practice for random data
  • O(n²) worst case possible but unlikely with random inputs
  • Not stable — unsuitable when tie order matters

Merge Sort:
  • Guaranteed performance regardless of input
  • Stable — preserves tie order, critical for fair ranking
  • Higher memory usage acceptable for small n

Recommendation: Use Merge Sort for production leaderboard generation.
